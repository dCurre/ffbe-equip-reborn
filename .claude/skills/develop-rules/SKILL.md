# Development playbook (FFBE Equip Reborn)

Read this before a development or analysis task. The roadmap of open work is `.claude/ROADMAP.md`;
committing/pushing follows the `push` skill.

## Rule #1 — Verify, never assume

Every statement about this codebase must come from checking the code, not from names, conventions or
memory. In practice:

- **Before saying something is used or unused**, search for it everywhere it could be referenced: JS,
  HTML, CSS (also `static/css-img/`), the JSON data files, `tools/`, `server/`, and paths built
  dynamically (string concatenation, template literals). If relevant, check git history
  (`git log -S "<string>" -- '*.js' '*.html' '*.css'`).
- **Before describing what a library or feature does here**, find its call sites with `git grep` and
  read them. A loaded library is not necessarily a used one.
- **Before asking the user to test something**, verify that the feature exists, on which page, and how
  it is triggered. Give test steps only for verified behaviour.
- **Two independent checks for important claims** (e.g. a strict regex search plus a looser one, or
  two sources for a downloaded file). If they disagree, find out why before concluding.
- **Say explicitly what you did NOT verify** ("not tested in the browser", "assumed from the docs").
- **When the design is genuinely ambiguous, ask** rather than guessing.

Search tips: prefer `git grep` (fast, tracked files only). Exclude minified libraries
(`':!static/lib/*'`) and the big data folders when they're not relevant (`':!static/GL/*' ':!static/JP/*'
':!tools/GL/*' ':!tools/JP/*'`). Never run a plain recursive grep over `static/img/`: it times out.

## How the project works (the facts the traps come from)

- **The site is static**, published by GitHub Pages under a sub-path
  (`https://dcurre.github.io/ffbe-equip-reborn/`) from the `static/` folder, by
  `.github/workflows/deploy-pages.yml` on every push to `master`. There is **no server online**:
  the old Node server was removed: anything still calling it (`/clientConfig`, `/partyBuild`, ...) is broken
  until migrated (see the roadmap). `npm start` only generates the unit files and serves `static/`.
- **Per-unit data files** `static/<server>/unit/<id>.json` are generated by
  `tools/generateUnitFiles.js` (on `npm start` and in the deploy) and git-ignored. The builder loads
  them; Unit Search loads the full `unitsWithSkill.json`.
- **Game data is frozen** (the game closed in 2024): `static/GL`, `static/JP`. Don't hand-edit the big
  JSON files unless the task is explicitly about data.
- **Node**: local development and the deploy both use Node 24 (`.node-version`).

## The traps (works locally ≠ works online)

### Paths
- Asset, data and page paths must be **relative** (`img/...`, `GL/units.json`, `./`), never
  root-relative (`/img/...`): online the site lives under `/ffbe-equip-reborn/`. Root-relative URLs are
  only acceptable for server APIs not migrated yet.
- Share links must be built from the current site URL (`getSiteBaseUrl()` in `static/common.js`),
  never from a hard-coded domain.
- GitHub Pages serves `index.html` as start page; the deploy copies `homepage.html` to it.

### HTML built by the scripts (jQuery 3.5+)
- Never write self-closing non-void tags in HTML strings (`<span .../>`, `<i .../>`, `<div .../>`):
  since jQuery 3.5 they are not auto-closed and the following markup ends up nested inside. Write
  `<span ...></span>`. Void tags (`<img .../>`, `<br/>`, `<input .../>`) are fine.

### Global function names
- The page scripts (`builder.js`, `units.js`, `contribute.js`, …) share the global scope with
  `static/common.js`: a `function foo()` in a page script silently REPLACES `foo` of common.js on that
  page, also for the calls made inside common.js. Before adding a top-level function, check the name is
  not already used: `git grep -n "function <name>(" -- 'static/*.js' 'static/builder/*.js'`.

### External resources, CSP and integrity
- The **Content-Security-Policy** is the `<meta>` tag in the 10 main pages (`static/*.html`): keep them
  identical. Adding a resource from a new domain (script, style, font, image, fetch/XHR) requires updating
  all of them, or it is blocked.
- CDN resources use `integrity` (SRI) + `crossorigin="anonymous"`. Compute the hash from the downloaded
  file (sha384) and cross-check it with a second source (the official published hash, or the same file
  from the npm package via jsDelivr). Never paste a hash from memory unverified.
- Download third-party files into a new empty folder in the scratchpad, inspect them (version header,
  size), then copy into the project.
- Prefer cdnjs / code.jquery.com / jsDelivr; avoid fragile third-party proxies.

### Browser storage
- `localStorage` holds only small settings (theme, user settings). Do not cache data files there: the
  browser HTTP cache already does it and the ~5 MB quota is too small (`QuotaExceededError`).

### Editing files on Windows (CRLF)
- The repo uses `core.autocrlf=true`; working files are CRLF. When editing with scripts (perl/node),
  preserve the file's line endings (the diff check is in the `push` skill).
- If an exact-match edit fails, the file may contain different whitespace: read the exact lines first,
  or replace by verified line range.

### Credits and identity
- Never remove or weaken the credits to Lyrgard (FFBE Equip), Ben Sailors (FFBE Equip Next) and their
  contributors (README, LICENSE, footer of every page, `package.json`).
- Don't leave references to the original project's accounts (analytics, Discord, donations, old
  domains) in new code.

## Working principles

- **Keep the user in the loop on testing**: after a change that affects what the site loads, give
  concrete, verified test steps (page, action, expected result, console to watch). The user tests
  locally before anything is committed or pushed (`push` skill).
- **No silent debt**: don't leave debug `console.log` in new code, don't hard-code what should come from
  data or the current URL, don't swallow errors without a reason.
- **Small, separate steps**: work on one topic at a time, so each can be tested alone. How to group
  them into commits is in the `push` skill (commit policy).
- **Use the dependency manager for dependencies**: give the user the `npm install/uninstall` command
  (they prefer to run npm themselves) instead of hand-editing `package.json`/`package-lock.json`.
